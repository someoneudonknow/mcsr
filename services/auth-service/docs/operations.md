# Operations

## Configuration

Config is layered: `src/config/envs/default.ts` merged with
`src/config/envs/<NODE_ENV>.ts` (`dev` by default), read from
`.env.<NODE_ENV>`. Access it through `ConfigService`, never `process.env` —
the one exception is `organization.module.ts`, which needs a value while the
module graph is still being built.

### Environment variables

| Variable | Default | Notes |
|---|---|---|
| `NODE_ENV` | `dev` | Picks both the env file and the config layer |
| `APP_PORT` | `3000` | **`3001` in `.env.dev`** |
| `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASS` / `DB_NAME` | — | `synchronize: true` in dev, `false` in prod |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_USERNAME` / `REDIS_PASSWORD` / `REDIS_DB` | — | |
| `JWT_CURRENT_KID` / `_PRIVATE_KEY` / `_PUBLIC_KEY` | — | **Required.** Base64-encoded PEM. Service refuses to boot without it |
| `JWT_PREVIOUS_KID` / `_PRIVATE_KEY` / `_PUBLIC_KEY` | — | Verify-only slot for rotation. Leave `_PRIVATE_KEY` empty |
| `JWT_ISSUER` | `mcsr-auth` | Must match the gateway plugin's `issuer` |
| `JWT_AUDIENCE` | `mcsr-api` | Must match the gateway plugin's `audience` |
| `JWT_ACCESS_TOKEN_EXPIRATION` | `15m` | Also your revocation window |
| `JWT_REFRESH_TOKEN_EXPIRATION` | `7d` | |
| `SESSION_TTL_SECONDS` | `604800` | **Keep in sync with the refresh TTL** |
| `KAFKA_BROKERS` | — | Comma-separated. Host: `localhost:19092,…`; in-cluster: `kafka-1:9092,…` |
| `KAFKA_CLIENT_ID` | `auth-service` | Nest appends `-server` / `-client` |
| `KAFKA_GROUP_ID` | — | Nest appends `-server`; becomes `auth-service-group-server` |
| `ORGANIZATION_GRPC_URL` | — | e.g. `localhost:50051`. **Currently unset in `.env.dev`** — add it before org-service goes live |

A missing or empty `JWT_CURRENT_KID` surfaces as
`No JWT signing key configured` at startup. That is intentional:
misconfiguration should kill the process, not appear as a 500 on someone's first
login. Watch for duplicate keys in `.env` — dotenv takes the **last** occurrence
silently, and an accidental empty redeclaration reads as "unset".

## Data model

All in auth-service's own `auth_db`. No foreign keys cross a service boundary.

### `identities`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | **App-generated UUIDv7**, not a DB default. Also the PK of `core.users` in the tenant DB |
| `tenant_id` | uuid | Logical reference to org-service. No FK — different database |
| `email` | varchar(255) | |
| `password_hash` | varchar | bcrypt |
| `role` | enum | `owner` / `admin` / `member` |
| `status` | enum | `pending` / `active` / `suspended` |
| `email_verified_at` | timestamptz | |
| `created_at` / `updated_at` / `deleted_at` | timestamptz | Soft delete |

`UNIQUE (tenant_id, email)` — **not** unique on email alone. The same person can
own accounts in two tenants; those are two separate identities.

### `tenant_refs`

Read-model projection of org-service. A **cache**, never a source of truth.

| Column | Type | Notes |
|---|---|---|
| `tenant_id` | uuid PK | Generated by org-service, copied here |
| `slug` | varchar(63) UNIQUE | 63 = the Postgres identifier limit, because it names a database |
| `can_auth` | boolean | Gates new logins |
| `max_seats` | int | For future seat-quota checks |

Keep it to these four columns. The moment `tier` or `name` appears, auth-service
has started owning organization data.

### `email_verifications`

`identity_id`, `token_hash` (char(64), SHA3-256, unique), `expires_at`,
`consumed_at`. Single-use; 24h TTL.

### `outbox_events`

`event_type`, `partition_key`, `payload` (jsonb), `published_at`, `attempts`.
Partial index on `created_at WHERE published_at IS NULL`.

## Redis keys

All built by `AuthRedisKey` — never hand-roll one, the gateway's ACL depends on
the prefix shape.

| Key | Type | TTL | Written by |
|---|---|---|---|
| `auth-service:session:<tenantId>:<userId>` | hash `{refreshJti}` | `SESSION_TTL_SECONDS`, slides on refresh | `SessionService.start` / `rotate` |
| `auth-service:refresh-token:used:<tenantId>:<userId>` | set of jti | same | `SessionService.rotate` |
| `auth-service:session-version:<tenantId>:<userId>` | integer | **none, by design** | `bumpSessionVersion` |
| `gateway:tenant-status:<tenantId>` | string | none | **org-service**, not this service |

## Kafka

Topics are **not** auto-created (`KAFKA_AUTO_CREATE_TOPICS_ENABLE=false`). From
the repo root:

```bash
make init-kafka-topic
```

| Topic | Direction | Partition key | Payload |
|---|---|---|---|
| `auth.owner_email_verified.v1` | **out** | `tenantId` | `{ tenantId, identityId, email, verifiedAt }` |
| `organization.activated.v1` | **in** | `tenantId` | `{ tenantId, slug, maxSeats }` |
| `organization.suspended.v1` | **in** | `tenantId` | `{ tenantId }` |

3 partitions, replication factor 3.

### Publishing: the outbox

Events are **never** published directly from a request. Writing to Kafka inside
a transaction is a dual write: the database commits and the publish fails (or the
reverse) and the tenant ends up verified but never provisioned.

Instead, `TenantAuthService` inserts an `outbox_events` row in the same
transaction as the state change, and `OutboxRelayService` polls every **1s**,
publishes up to **100** rows oldest-first, and gives up on a row after **10**
attempts. Delivery is therefore at-least-once, which is why every consumer must
be idempotent.

### Consuming

`OrganizationEventsController` uses `@EventPattern`. Ordering is safe without a
version field because the partition key is `tenantId` and Kafka guarantees order
within a partition — `activated` then `suspended` for one tenant cannot arrive
reversed.

Idempotency comes from the writes themselves: `upsert` on the `tenant_refs` PK,
and a status-filtered `UPDATE` on the owner identity that matches zero rows on a
redelivery. No dedup table.

**Caveat worth knowing:** with `@EventPattern`, a handler that throws is logged
and **the offset still commits** — the event is dropped. The only realistic
failure is the database being down, at which point the service is broken anyway.
If you want a safety net, the cheap version is a reconciliation job that asks
org-service about any tenant whose local `can_auth` disagrees — not a DLQ.

### Broker addressing

Each broker exposes two listeners, because no single address works from both
sides. A client only uses `KAFKA_BROKERS` to bootstrap; everything after that
goes to whatever the broker **advertises**.

| From | Use |
|---|---|
| Host (`pnpm start:dev`) | `localhost:19092,localhost:29092,localhost:39092` (EXTERNAL) |
| Inside docker | `kafka-1:9092,kafka-2:9092,kafka-3:9092` (INTERNAL) |

`KAFKA_INTER_BROKER_LISTENER_NAME=INTERNAL` is required — if replication used
EXTERNAL, each broker would dial `localhost` and reach itself.

## gRPC to org-service

`proto/organization/v1/organization.proto` — `ReserveSlug`, `ReleaseSlug`.
Constants live in `organization/constants/organization-grpc.constants.ts`:
`ORGANIZATION_GRPC_PACKAGE` must equal the proto's `package`, and
`ORGANIZATION_GRPC_SERVICE` its `service` name. Both are resolved at runtime
against the parsed proto, so a mismatch gives `InvalidGrpcServiceException` at
**boot**, not on the first call — proto parsing is local and does not need
org-service running.

2s timeout via rxjs. Note this is *not* a gRPC deadline: it unsubscribes on the
client while the server keeps working, so a timed-out `reserveSlug` may still
have reserved the slug. That is exactly why `idempotencyKey` exists — the
timeout and the key are one design, not two features.

`nest build` does not copy `.proto` into `dist/`. The path resolves from
`process.cwd()`, which works from the project root; if you ever run from inside
`dist/`, add `"assets": ["**/*.proto"]` to `nest-cli.json`.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `No JWT signing key configured` | `JWT_CURRENT_*` missing, or a duplicate empty redeclaration later in `.env` |
| `UNKNOWN_TOPIC_OR_PARTITION` at boot | Topics not created → `make init-kafka-topic` |
| `InvalidGrpcServiceException` | `getService()` got the package name instead of the service name |
| `ENOENT ... organization.proto` | Wrong `ORGANIZATION_GRPC_PATH`, or running from a directory that is not the project root |
| Consumer never joins | No `consumer.groupId` in `main.ts`, or topics missing. Check for the `Consumer has joined the group` log line and its `memberAssignment` |
| `No security protocol defined for listener INTERNAL` | A broker's `KAFKA_LISTENER_SECURITY_PROTOCOL_MAP` lacks the custom listener names |
| `503 Organization service unavailable` on register | Expected while org-service is not running |
| Login returns `TENANT_BLOCKED` with a correct slug | No `tenant_refs` row yet — activation event never arrived |
| Login returns `TENANT_NOT_READY` | `can_auth = false`, or the identity is still `pending` |
| Tokens rejected by the gateway | `JWT_ISSUER` / `JWT_AUDIENCE` mismatch between this service and the plugin config. Check this first |

### Useful queries

```sql
-- unpublished outbox rows (should drain within ~1s)
SELECT event_type, attempts, created_at FROM outbox_events WHERE published_at IS NULL;

-- tenants that can authenticate
SELECT slug, can_auth FROM tenant_refs ORDER BY updated_at DESC;

-- identities stuck pending (provisioning never completed)
SELECT email, status, created_at FROM identities WHERE status = 'pending';
```

```bash
# simulate org-service activating a tenant
docker exec -it mcsr_kafka_1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:9092 --topic organization.activated.v1 \
  --property parse.key=true --property key.separator='|'
# <tenantId>|{"tenantId":"<tenantId>","slug":"acme","maxSeats":5}

# what is published right now
curl -s localhost:3001/.well-known/jwks.json | jq '.keys[].kid'

# consumer group lag
docker exec mcsr_kafka_1 /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server kafka-1:9092 --describe --group auth-service-group-server
```

## Known gaps

Things a maintainer will trip over, in rough priority order.

1. **No verification email is sent.** `TenantAuthService.register` has a
   `// Send verification email here.` placeholder; the raw token currently goes
   nowhere. Signup is unusable end-to-end until a mail transport is wired in.
   There is also no resend endpoint for expired tokens.
2. **`ErrorResponseFilter` is never registered.** It and `ErrorMessages` are dead
   code, so clients receive Nest's default error shape with a raw enum value as
   `message`. Register it as `APP_FILTER` to get `{ success, message, code,
   statusCode }` and human-readable text.
3. **No rate limiting.** `/tenants/register` and `/auth/login` need `limit-req`
   at the gateway — one allocates a database, the other is a credential-guessing
   surface.
4. **`outbox_events` is never pruned.** Published rows accumulate forever. Add a
   job that deletes `published_at < now() - interval '7 days'`.
5. **No tests.** There is no `test/` directory, so `pnpm test:e2e` fails on a
   missing Jest config. The highest-value first targets are the login
   enumeration guarantees (unknown email and wrong password must be
   indistinguishable), refresh replay detection, and consumer idempotency.
6. **No invite flow.** Only tenant-owner signup exists. Adding a member to an
   existing tenant has no endpoint yet; see the invitation design notes in
   [`flows.md`](./flows.md).
7. **`emailVerifiedAt` is set but never checked at login.** Status is the only
   gate today. Fine while activation implies verification, but worth tightening
   if invited members can set a password before verifying.
